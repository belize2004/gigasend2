# SEO-LOCALE-002 — hreflang emitted from a verified reciprocal cluster map

Date: 2026-10-28
Scope: `src/layouts/BaseLayout.astro`, 27 page files, `src/data/hreflangClusters.ts`, 3 scripts
Status: implemented, built, verified — **not deployed**

## Problem

Every page hand-rolled its own `hreflang` array, and the arrays disagreed with the
actual translations. Measured on all 554 live sitemap URLs:

| live symptom | count |
|---|---|
| ES landing pages emitting a lone self-referencing tag | 293 |
| PT landing pages emitting only `en` + `pt-BR` (+ a stray `es` link = 2–4 tags) | 104 of 159 |
| pages claiming a complete 4-way cluster | 144 |
| ...of those, pointing at pages that do not point back | 81 |
| pages missing `x-default` | 397 |
| ES regional pages (`/es/mexico` etc.) in 5-tag clusters nothing reciprocated | 4 |

The three template defects:

```astro
// src/pages/es/[slug].astro — 4 tags if the pair is canonical, otherwise a lone self tag
const hreflang = page.isCanonicalEnPair ? [ en, es, pt-BR, x-default ] : [{ es: canonical }];

// src/pages/pt/[slug].astro — never mentions ES at all
const hreflang = landingPage.isCanonicalEnPair ? [ en, pt-BR, x-default ] : [{ pt-BR: canonical }];
// plus a second <link rel="alternate" hreflang="es" ...> in <head>, which is NOT reciprocal

// src/pages/[slug].astro — always 4 tags, derived from the navbar switcher
const hreflang = [ en, es: esPath || "/es", pt-BR: ptPath || "/pt", x-default ];
```

The last one is the worst: `getLanguageSwitchPaths` is a *navigation fallback* ("closest
page we have in that language"). It happily returns `/`, `/es` or `/pt` when no real
translation exists, so ~50 EN pages advertised a translation that is really just the
locale home page. `staticTriplets` has the same property: 4 of its 11 entries contradict
the target page's own `enEquivalent` (e.g. `/plans` → `/es/transferencia-archivos-pago-por-uso`,
a page whose `enEquivalent` is `/transfer-large-files-online`).

Live output is **not** stale cache: `/es/mexico` returns the exact 5 tags declared in
`src/pages/es/mexico.astro`, `/pt/planos` returns the declared 3-tag array plus the stray
`es` link, and the 1/2/4/5-tag distribution per section is reproducible from these
templates alone.

## Change

`BaseLayout.astro` is now the only emitter:

```astro
const effectiveHreflang = hreflang.length > 0 ? hreflang : getHreflangCluster(pathname);
```

The `hreflang` prop survives as an escape hatch but no page uses it. Every per-page
array, every `hreflang={...}` attribute and every stray `<link rel="alternate" hreflang="es">`
slot was removed (27 files, `scripts/remove-hreflang.mjs`).

`src/data/hreflangClusters.ts` is generated by `scripts/build-hreflang-clusters.mjs`
(`prebuild` hook, also `npm run seo:hreflang`). A candidate cluster is emitted only if:

1. every target is a real route (derived from the `.astro` files on disk + the locale data sets),
2. every member agrees on the stated file size (`5gb` vs `3gb` is a conflict, not a translation),
3. each URL belongs to exactly one cluster — hreflang is 1:1 and cannot express N:1,
4. the ES member's `ptEquivalent` points back at the PT member (mutual reciprocity),
5. the cluster has at least two members.

Hand-verified `.astro` hubs are listed explicitly in `STATIC_CLUSTERS` and are trusted
ahead of the data sets. They are exempt from the size heuristic because the check there
is a human read: `/send-files-larger-than-2gb` ↔ `/pt/enviar-arquivo-2gb-3gb-gratis` is
the same family even though one slug names a superset.

Pages with no verified counterpart emit **nothing**. A lone self tag is ignored by Google
and only hides the fact that the cluster is broken.

## Result

47 clusters / 120 URLs: 25 `en+pt-BR`, 21 `en+es+pt-BR`, 1 seven-way
(home + `es-MX`/`es-ES`/`es-CO`/`es-AR`). 28 candidates rejected by the guards.

`node scripts/verify-hreflang.mjs dist` over 600 built pages:

```
hreflang tag count distribution: { '0': 482, '3': 49, '4': 63, '8': 6 }
distinct clusters: 47   lone self tag: 0   non-reciprocal: 0   problems: 0   PASS
```

Before → after on the 554 live sitemap URLs:

| | live | after |
|---|---|---|
| lone self tag | 293 | 0 |
| pages emitting a verified cluster | 144 (81 fabricated) | 118 |
| pages emitting nothing | 7 | 428 |
| pages with `x-default` | 157 | 118 |

The 293 ES pages that drop to zero tags are exactly the near-duplicate size/verb family
members scheduled for 301 in Phase 2 (`SEO-LOCALE-001`); they have no translation to
claim yet, and will acquire one when they collapse into the two ES hubs.

## Deploy notes

1. `npm run build` regenerates the cluster map first (`prebuild`); commit the regenerated
   `src/data/hreflangClusters.ts` with any data change.
2. `npx wrangler deploy` from the repo root.
3. Re-crawl a sample of `/es/mexico`, `/pt/planos` and one 3-way page and confirm the new
   tags are live. HTML is served with `cf-cache-status: HIT` even for a unique query
   string (query-string-insensitive zone cache key) but `cache-control: public, max-age=0,
   must-revalidate`, so it revalidates. If a page still serves the old tags, purge the zone
   cache for `gigasend.us` (`80eaddefa7238068cc7507454ec3cc11`).
4. Re-run `node scripts/verify-hreflang.mjs dist` in CI before deploying.

## Follow-ups

- **Phase 2 (`SEO-LOCALE-001`)**: build the two hubs, apply the 178 redirects, prune the
  sitemaps, then **re-run `scripts/build-hreflang-clusters.mjs`** — the hubs become cluster
  targets and the 293 tag-less ES pages either disappear or gain a real twin.
- 13 ES/PT URLs are claimed by two different English pages and lose their tags under the
  1:1 guard; they need to be resolved during the consolidation, not by hreflang.
- `src/pages/send/[slug].astro` declares `canonical` as `/${slug}` while being served at
  `/send/${slug}`, so it never matches a cluster and emits nothing. Pre-existing, out of scope.
